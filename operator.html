  3. 개최 전날·당일: 대상 인원·환경 대장·만료 시각·문의 경로·운영자 대체 담당을 확정하고, 모델 가용성과 권한·로그 동작을 다시 확인합니다.

OPERATOR PERMISSIONS ARE NOT PARTICIPANT PERMISSIONS

Entra 계정 관리와 Azure 자원 관리를 구분합니다.

아래는 준비 작업에 필요한 권한 구성이지 특정 SE 계정의 실제 역할 감사 목록이 아닙니다. 한 사람이 모두 보유할 필요가 없으며, 기존 승인된 담당자에게 작업을 나눌 수 있습니다.

필요할 때만정책·인증 담당자의 해당 Entra 역할조건부 액세스 변경은 Conditional Access Administrator, 비관리자 참가자 인증 방법 초기화는 Authentication Administrator 등 해당 권한의 담당자에게 요청합니다. 기존 정책을 유지하면 정책 변경 역할을 추가할 이유가 없습니다.
이미 구독 Owner인 Azure 담당자는 Contributor + RBAC Administrator 작업을 수행할 수 있으므로 중복 할당하지 않습니다. Contributor + User Access Administrator도 대안입니다. Azure Owner는 Entra User Administrator를 대체하지 않으며, Entra Global Administrator도 기본적으로 Azure Owner가 아닙니다. Entra 관리자 역할을 최초 부여하는 작업은 기존 권한 담당자에게 요청합니다.
위 운영자 역할을 참가자에게 복사하지 않습니다. 참가자의 Entra 관리자 역할은 없음이 기본이며, Azure 역할은 본인 RG의 Contributor·Foundry User와 구독의 Cognitive Services Usages Reader를 기준으로 합니다. 최종 리허설은 참가자 계정이 직접 리소스를 생성·실행하는 방식으로 합니다.

ONE IDENTITY PER PARTICIPANT

계정 유형과 로그인 방법을 함께 전달합니다.

기본 예시는 workforce 테넌트의 Internal Guest입니다. 테넌트 내부 자격 증명으로 로그인하지만 디렉터리 기본 권한은 Guest 수준입니다. Guest는 Azure 역할 이름이 아닙니다.

  1. Entra admin center에서 대상 테넌트 확인 → Entra ID → Users → New user → Create new user.
  2. 참가자별 고유 UPN·표시 이름·초기 암호를 준비하고, Properties → Identity → User type=Guest를 선택합니다. 계정 활성 상태를 확인하고 Entra 관리자 역할은 할당하지 않습니다.
  3. 대상 테넌트의 사용자 Object ID를 운영 대장에 기록합니다. 비슷한 표시 이름이나 외부 계정의 홈 테넌트 Object ID로 Azure 역할을 잘못 할당하지 않습니다.
  4. 초기 암호는 가이드·GitHub·영상·일반 고객 명단과 분리된 승인된 경로로 전달합니다. 첫 로그인·필요한 암호 변경·MFA 등록은 참가자가 직접 완료합니다.
  5. 실제 고객 기기·네트워크에서 로그인과 MFA를 미리 시험합니다. “5시간 실습”이 인증 정책 예외나 세션 만료를 없애 주지는 않습니다.
Internal Member도 사용할 수 있지만 필수는 아닙니다. Member 변경은 디렉터리 기본 접근에 영향을 주고 Azure RBAC를 대신하지 않습니다. External Guest는 Invite external user로 초대하고 외부 계정으로 인증하는 다른 시나리오입니다. 초대 수락·cross-tenant access·조건부 액세스·MFA 신뢰를 점검하고 별도 E2E를 수행하세요.
이 워크샵은 Azure Portal을 사용하는 workforce 테넌트 시나리오입니다. 고객 앱 로그인용 Entra External ID 외부 테넌트·B2C 계정을 같은 방식으로 취급하지 않습니다. Guest 접근 제한이 나타나면 우선 정책과 권한 범위를 확인하고, 일괄 Guest → Member 전환이나 Guest 디렉터리 접근 제한 해제를 해결책으로 삼지 않습니다.

RESOURCE GROUP FIRST · IDENTITY-SPECIFIC RBAC

고객별 RG와 사용자 역할을 준비하고, MI도 따로 점검합니다.

  1. Azure Portal → Subscriptions에서 대상 구독·테넌트와 운영자 권한을 확인합니다. Resource providers에서 실습에 필요한 RP의 Registered 상태를 확인하고 필요한 공급자만 등록합니다.
  2. Resource groups → Create에서 rg-fdry-<workshop-id>-<participant-id> 같은 고유 이름으로 RG를 생성합니다. 고객별 매핑과 Workshop ID·만료 시각 등 비민감 태그를 운영 대장에 기록합니다.
  3. 각 RG → Access control (IAM) → Add role assignment에서 해당 참가자에게 Contributor + Foundry User를 할당합니다. 구독 IAM에서는 Cognitive Services Usages Reader를 할당합니다. 실습자 필수 역할·범위와 대조합니다.
  4. 인계할 고객 RG에는 실습용 Foundry·프로젝트·모델·관측성 리소스를 미리 만들지 않습니다. 모든 참가자를 묶은 그룹에 모든 개인 RG의 Contributor·Foundry User를 주지 않습니다.
  5. 역할 이름·GUID·대상 Object ID·실제 Scope·상속·그룹 멤버십을 Check access로 확인합니다. 모델 배포 검증에 필요한 Usages Reader는 RG가 아닌 구독 범위입니다.

고객용 실제 오류 화면 · RP 등록 권한·절차

사용자 RBAC와 프로젝트 Managed Identity는 별개입니다.

권한을 받는 주체SE 확인·할당시점·주의점
참가자 사용자본인 RG의 Contributor·Foundry User와 구독의 Usages Reader.워크샵 전에 준비합니다. 사용자에게 역할을 줘도 프로젝트 MI에 같은 역할이 생기지 않습니다.
프로젝트 MI공식 시작 기준의 Foundry User · 부모 Foundry 리소스를 확인하고 필요한 미할당 권한은 SE가 지원합니다.참가자가 프로젝트를 생성한 이후 MI Object ID를 확인합니다. 인계 전 프로젝트를 만드는 절차가 아닙니다. 역할 할당 권한 없는 생성자의 UI 자동 할당을 가정하지 않습니다.
도구·연결 실행 신원실제 인증 주체가 사용하는 Search·Storage 등 대상 서비스의 데이터 권한.인증 방식에 따라 사용자·프로젝트 MI·Foundry 리소스 MI 등이 다릅니다. 조회 전용이면 필요한 Reader 데이터 역할부터 검토하고 쓰기·역할 할당 권한은 별도로 판단합니다.
기존 기본 Agent E2E는 tools=[]이며 사용자 역할 3개를 확인했습니다. 공개 검증 JSON은 MI의 완전한 권한 감사 자료가 아닙니다. 도구·SDK·Hosted Agent·게시 등으로 확장할 때 이 결과만으로 충분한 권한이라고 일반화하지 않습니다.

공식 Foundry 사용자·MI·프로젝트 Scope 기준. Foundry User의 이전 이름은 Azure AI User이며 역할 ID는 53ca6127-db72-4b80-b1b0-d745d6d5456d로 동일합니다. 자동화 시 이름 변경을 고려해 GUID를 확인합니다.

MI나 연결 대상의 권한 지원이 필요해도 참가자에게 Owner·RBAC Administrator를 주지 않습니다. 참가자는 리소스를 생성하고, SE는 필요한 권한만 지원한다는 경계를 유지합니다.

CAPACITY IS SHARED · BUDGET IS NOT A STOP SWITCH

50개 RG를 만들기 전에 모델 쿼터와 비용을 계산합니다.

그룹별 모델·버전·지역·배포 유형을 정한 뒤 현재 할당량·잔여 쿼터·리소스 수 한도·실제 공급 가용성을 확인합니다. 문서의 기본값만으로 50명 개최 가능을 확정하지 않습니다.

확인 항목운영 기준
TPM 할당예를 들어 같은 쿼터 풀에서 50명 × 개인 배포 10,000 TPM = 500,000 TPM의 배포 할당이 필요합니다. 기존 배포 할당과 별도로 잔여량을 확인합니다. 이는 예상 사용 토큰이나 비용이 아니라 속도 한도 할당입니다.
쿼터 공유 ScopeFoundry Quota의 Scope 열을 확인합니다. Global·Data Zone이면 해당 구독 전체·데이터 존의 풀을, 지역명이면 해당 지역의 풀을 공유합니다. 같은 모델을 다른 RG·지역·버전에 추가한다고 독립 쿼터가 생긴다고 가정하지 않습니다.

  2. 보존 승인: 로그·프롬프트·출력의 고객 데이터 취급, 보존 기간과 필요한 내보내기를 확인합니다. 전체 로그를 공개 가이드나 영상으로 복사하지 않습니다.
  3. 접근 회수: 직접 Azure 역할과 그룹을 통한 접근을 확인해 승인된 순서로 회수합니다. 계정 차단·필요한 세션 회수는 Entra 담당자가 수행하고, 이미 발급된 토큰과 권한 전파 지연을 고려해 다시 확인합니다.
  4. 자원 정리: 운영 대장·태그로 해당 워크샵의 정확한 RG와 리소스를 확인하고 승인된 대상만 정리합니다. RG 삭제는 Foundry·모델·프로젝트·로그를 함께 없앨 수 있으며, soft-delete·복구·보존 정책도 확인합니다.
  5. 종료 검증: 역할·계정 상태·남은 배포·로그·비용을 재확인합니다. 사용자 삭제만으로 Azure RBAC 할당이 모두 지워진다고 가정하지 않습니다.
이 가이드에는 자동 삭제 기능이 없습니다. 구독 전체 삭제·이름 패턴만 보고 일괄 삭제·로그 보존 결정 전 RG 삭제를 하지 않습니다. 다음 워크샵은 새 고유 이름·최신 모델 가용성·새 리허설 결과를 기준으로 준비합니다.
