WHO DOES WHAT

운영자는 준비하고, 실습자는 만들고 실행합니다.

Entra ID 역할은 계정·디렉터리 관리 권한입니다. Azure RBAC 역할은 구독·RG·Foundry 리소스 접근 권한입니다. 둘은 서로 대체되지 않습니다.

Guest는 관리자 역할이 아닌 사용자 유형입니다. 이 실습은 테넌트 내부 계정을 userType=Guest로 만든 Internal Guest입니다. 외부 계정 초대용 Guest Inviter만으로 내부 계정을 생성하는 시나리오가 아닙니다.

운영자 · 실습 전 준비와 종료 후 정리

아래는 이 작업에 필요한 운영자 권한 구성입니다. 현재 관리자 계정이 가진 모든 역할을 감사한 목록은 아닙니다. 계정 관리자와 Azure 운영자가 다른 사람이어도 됩니다.

권한 체계운영자가 보유할 역할범위 · 담당 작업
Entra IDUser Administrator대상 테넌트 · 내부 계정 생성·관리, 초기 암호 발급·계정 차단. Create new user → Properties → User type=Guest를 지정합니다.
Azure RBACContributor실습 구독 · 고객별 배정 RG 생성, 필수 리소스 공급자(RP) 등록, 리소스·모델 쿼터 확인. Contributor만으로는 RBAC 역할을 할당할 수 없습니다.
Azure RBACRole Based Access Control Administrator실습 구독 · 참가자에게 본인 RG의 Contributor·Foundry User와 구독의 Cognitive Services Usages Reader를 할당·회수합니다. Microsoft.Authorization/roleAssignments/write 권한이 필요합니다.
기존 구독 Owner가 있다면 위 Azure RBAC 두 역할의 작업을 수행할 수 있으므로 둘을 추가로 할당할 필요는 없습니다. Contributor + User Access Administrator도 대안입니다. 새 운영자에게는 필요한 권한만 부여하고, 가능하면 RBAC 할당 조건으로 대상 역할·참가자를 제한합니다. Azure Owner는 Entra User Administrator를 대체하지 않으며, Entra Global Administrator도 기본적으로 Azure Owner가 아닙니다.
  1. 계정 준비: 참가자별 Internal Guest 계정 생성, 초기 암호를 별도 안전한 경로로 전달, 첫 로그인·MFA 등록 방법 안내. 암호나 인증 코드를 공개 가이드에 올리지 않습니다.
  2. Azure 준비: 고객별 RG 생성 → 아래 실습자 역할 3개 할당 → 필수 RP 사전 등록 → 모델 지역·쿼터·50명 동시 사용 계획 확인. 이 가이드에서는 RG까지만 운영자가 만들고 Foundry·프로젝트는 참가자가 만듭니다.
  3. 시작 전 확인: 참가자의 로그인·구독 필터·배정 RG 접근 확인, 다른 고객 RG 접근 차단 확인, 권한 전파 대기 및 RP 오류 처리. 구독 오퍼의 고객 교육 사용 허용 여부·비용·로그 보존 정책도 확인합니다.
  4. 종료 후 처리: 완료 기록과 로그 보존 확인 → 승인된 정책에 따라 RBAC 회수·계정 차단·리소스 정리. 이 문서와 영상은 계정이나 Azure 자원을 자동 삭제하지 않습니다.

MFA는 참가자가 직접 등록합니다. 기존 정책을 유지하면 운영자에게 MFA 정책 변경 역할을 추가할 필요는 없습니다. 조건부 액세스를 변경할 때만 Conditional Access Administrator, 비관리자 참가자의 인증 방법을 초기화할 때만 Authentication Administrator 등 해당 작업 권한을 가진 별도 담당자가 처리합니다. 운영자에게 Entra 관리자 역할을 최초 부여하는 작업은 Privileged Role Administrator 또는 기존 Global Administrator의 영역입니다.

실습자 · 본인 RG 안에서 생성·실행·추적

권한 체계실습자가 보유할 역할범위 · 담당 작업

Azure RBACContributor본인에게 배정된 RG만 · Foundry 리소스·기본 프로젝트·모델 배포·Log Analytics·Application Insights 생성 및 관리. 구독 전체 Contributor를 주지 않습니다.

Azure RBACCognitive Services Usages Reader실습 구독 · 지역별 Cognitive Services 사용량·쿼터 조회. 이 조회 역할만 구독 범위이며, 구독 전체 리소스 생성·RBAC 할당 권한은 아닙니다.
  1. 로그인·범위 확인: 발급된 계정으로 첫 로그인·MFA를 완료하고 올바른 테넌트·구독·본인 RG 및 세 RBAC 역할을 확인합니다.
  2. 직접 생성: Azure Portal에서 Foundry + 기본 프로젝트 생성 → Foundry Portal에서 GPT-5 mini 배포·테스트 → Instructions를 작성하고 기본 Prompt Agent 저장.
  3. 관측성 연결: 본인 RG에 Log Analytics + Application Insights 생성 → 프로젝트에 기존 App Insights 연결 → 연결 이후 새 대화 실행.
  4. 결과 확인: 실제 응답·Monitor·Traces를 확인하고 입력·출력·토큰·Guest 실행자를 대조한 뒤 운영자에게 완료를 알립니다.
실습자가 하지 않는 작업: 다른 사람 계정 생성, 다른 참가자 역할 할당, 새 고객 RG 생성, 구독 RP 등록, 조건부 액세스·MFA 정책 변경, 다른 고객 RG 접근, 승인 없는 RG·로그 삭제. RG Contributor는 본인 RG 안에서 삭제 권한도 있으므로 작업 정책을 반드시 지킵니다. 이 검증에는 Owner·Foundry Project Manager·Guest → Member 전환이 필요하지 않았습니다.

Internal Guest는 이 검증에서 Entra userType=Guest인 테넌트 내부 도메인 계정입니다. 외부 B2B 초대 계정으로 일반화하지 않습니다. 운영자는 계정·초기 암호를 별도 안전한 경로로 전달하고, 참가자가 MFA·첫 로그인 절차를 직접 완료하게 합니다.

이 검증에서는 Guest → Member 전환, Owner·구독 Contributor·Foundry Project Manager 추가 없이 진행했습니다. 참가자는 역할을 직접 추가하지 않습니다. 새 역할이 포털에 반영되지 않으면 운영자가 할당을 확인한 후 새로고침·재로그인합니다.

리소스 공급자(RP)를 운영자가 구독에 사전 등록합니다. 이번 구독에서는 다음 공급자의 Registered 상태를 확인했습니다.

Microsoft.CognitiveServicesMicrosoft.OperationalInsightsMicrosoft.InsightsMicrosoft.StorageMicrosoft.SearchMicrosoft.ManagedIdentityMicrosoft.KeyVaultMicrosoft.DocumentDB

특히 이 포털 생성 화면은 Microsoft.KeyVault와 Microsoft.DocumentDB 미등록 시 사전 검증에서 실패했습니다. 운영자가 등록만 수행한 뒤 Guest 생성이 성공했습니다. Key Vault·Cosmos DB를 별도로 만들거나 Guest 권한을 넓힌 것이 아닙니다.

50명·5시간 운영은 별도 준비 대상입니다. 이 문서는 Guest 1명의 E2E 검증입니다. 모델·리소스 수 한도, 지역 가용성, 동시 부하, MFA/조건부 액세스, 비용·로그 보존, 구독 오퍼의 외부 고객 교육 사용 허용 여부를 운영자가 별도로 확인해야 합니다. 10,000 TPM은 속도 한도이지 비용 상한이 아닙니다.

녹화 계정에는 이전 E2E 검증용 RG 권한도 남아 있습니다. 실제 워크샵 계정은 고객별 본인 RG로 제한하고 다른 고객 RG 접근이 불가능한지 별도 확인하세요.
